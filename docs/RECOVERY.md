# GameShelf 数据安全、恢复与 Windows 验收

## 数据位置

Windows 安装版把所有受 GameShelf 管理的数据放在 `%APPDATA%\GameShelf`；便携版在 `GameShelf.exe` 旁存在 `gameshelf-portable` 标记时使用同级 `data` 文件夹：

- `gameshelf.sqlite`：游戏索引、设置、合集、启动项和游玩记录
- `backups`：自动备份、手动备份、迁移前备份与恢复前备份
- `logs/gameshelf.log`：主进程错误、崩溃和恢复记录
- `covers`、`backgrounds`、`profile`：GameShelf 复制并管理的图片

游戏本体、存档和游戏目录不在这些操作的写入范围内。完整迁移或人工归档时，应先退出 GameShelf，再复制整个 `data` 文件夹；只复制数据库备份不会包含图片。

## 备份与恢复

GameShelf 每天首次启动时创建一个经过完整性校验的数据库备份。数据库升级前和手动恢复前还会额外创建安全副本。

手动操作入口位于“设置 → 数据安全与诊断”：

1. “立即备份”在 `data/backups` 创建并校验一个新备份。
2. “从备份恢复”先验证文件是完整、受当前版本支持的 GameShelf 数据库。
3. 校验通过后，确认对话框会说明当前游戏库将先被备份；取消或校验失败都不会修改当前库。
4. 恢复成功后界面重新读取游戏库；封面、背景和任何游戏目录保持不变。

不要在 GameShelf 运行时手工替换 `gameshelf.sqlite`、`-wal` 或 `-shm` 文件。

## 异常退出

GameShelf 用运行标记识别上次是否正常退出。重新启动时：

- SQLite 自身恢复后若完整性校验通过，继续使用当前数据库，不回退较新的数据。
- 只有完整性校验失败时，才恢复最近的有效备份。
- 无法通过校验的原数据库会保存在 `data/backups`，文件名包含 `corrupt`，便于后续排查。
- 没有有效备份时，GameShelf 停止打开数据库并提示先复制整个 `data` 文件夹，不会创建空库覆盖原文件。

游戏使用独立进程组启动，并且不继承 GameShelf 的标准输入输出句柄。GameShelf 正常退出、更新或崩溃时不会主动终止已经启动的游戏。

## 导出诊断

“导出诊断”生成一个 JSON 文件，包含应用/系统版本、数据库版本与完整性、记录数量、启动恢复状态和最近日志。报告不包含游戏名称、启动路径或图片路径；日志中的用户目录会被替换。导出文件只写到用户选择的位置，不会自动上传。

## Windows 实机补充 Manual 清单

Windows 核心稳定性回归已经完成；以下项目保留为发布后的故障注入与极端环境补充，不应误写为 1.0 核心验证尚未执行：

- [ ] 在现有便携 `G:\GameShelf` 副本上先备份 `data`，再覆盖更新到 1.0，确认原游戏数、合集、设置和图片均保留。
- [ ] 对 `G:\GalGame` 与 `G:\game` 中的测试游戏各启动一次，退出 GameShelf，确认游戏继续运行；再让 GameShelf 异常结束并重复确认。
- [ ] 游戏运行期间重新打开 GameShelf，确认游戏库可读写，且退出游戏后游玩记录正常更新；若启动器先异常退出，只要求游戏不受影响，不虚构丢失区间的精确时长。
- [ ] 创建手动备份，修改一个可辨认的库字段，再恢复备份；确认恢复前副本存在、字段回退、游戏目录和图片未被改写。
- [ ] 选择损坏文件和更高数据库版本文件执行恢复，确认在确认对话框之前被拒绝，当前库不变且提示可操作。
- [ ] 使用任务管理器结束 GameShelf 后重新打开，确认提示上次异常退出；数据库正常时不回退，模拟损坏时从最近有效备份恢复并保留损坏原文件。
- [ ] 临时移动一个测试游戏的 `.exe`，确认启动提示引导到“游戏设置 → 启动项”重新选择，而不是只显示系统错误码。
- [ ] 触发一次可控的渲染进程异常，确认日志可读、界面可重新载入、诊断 JSON 可导出且不含游戏名称和启动路径。
- [ ] 在剩余空间不足或 `data` 不可写的测试副本中创建备份，确认错误明确提示检查空间与权限，原数据库仍可用。

这些 Manual 项目不改变已完成的 Windows 核心回归结论；执行时仍只能使用可丢弃副本。
